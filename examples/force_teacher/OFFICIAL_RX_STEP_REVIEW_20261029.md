# 官方 B601 收发逐步核对与 Owner 接收服务诊断

本轮先核对官方各层的实际行为，再定位本机接收服务耗时。保持唯一串口 Owner、每拍七轴新反馈、原 20 ms 组期限、安全检查频率及全部运动/力限参数。不将官方宽松缓存行为替换为 Teacher 的控制证据，也不以串行回退作为异步修复。

## 从启动到读取缓存的每一步

| 步骤               | 官方实际执行                                                                                                                             | 对本机 Teacher 的含义                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1. 建立总线        | `connect()` 创建 DM serial controller，按配置添加七个电机，再初始化相机和配置电机                                                        | 官方使用一个带互斥锁的串口总线；不能理解为七轴各自拥有独立串口                                |
| 2. 启动收包        | 添加设备触发后台接收线程；多电机默认发送间隔 120 µs，可用 `MOTORBRIDGE_TX_GAP_US` 显式覆盖                                               | 本机仍由既有 Owner 在发送间隙和两拍之间处理，不增加线程；本轮 1000 µs 配置不自动切换          |
| 3. 设置模式        | 先全轴失能，逐轴 `ensure_mode()`，随后全轴使能；批量操作另有默认 2 ms 节流                                                               | 模式查询/验证的等待和重试属于启动流程，不是正常控制拍，也不能据此扩大本机预算                 |
| 4. 取动作目标      | `send_action()` 提取各轴目标；配置了相对限制时先读取反馈再裁剪                                                                           | 本机继续使用决策时的七轴观察与本拍实际提交动作；保留目标裁剪和安全绑定                        |
| 5. 编码命令        | 六臂 MIT 由 `send_cmd_mit` 编码；FORCE_POS 由 `send_cmd_force_pos` 使用 `0x300+ID`，两者都进入相同 `send_raw` 和总线                     | FORCE_POS 没有另一套接收线程或额外收包等待分支；不能单凭夹爪排最后就归因为控制模式            |
| 6. 发送节流        | `TxPacedBus.send()` 检查上次发送起点；不足最小间隔则 sleep，随后调用底层发送                                                             | 官方也有等待；“异步”指不逐轴等待命令反馈，并不保证函数毫不阻塞                                |
| 7. 串口提交        | 编码一个 30 字节桥接包，取得共享串口锁，调用 `write_all()`                                                                               | 后台接收持有同一总线锁时，发送也可能等待锁；官方返回值不是设备执行 ACK                        |
| 8. 接收入口        | 接收线程用 `recv(0)`；先尝试解析本地缓冲。新增参考在零等待分支先检查 `bytes_to_read()`，无字节时避免进入读调用                           | 本机已检查可读字节，但 PySerial 内部还会再次查询；需测量各次查询与读模式切换                  |
| 9. 原生读法        | Rust Windows `COMPort.set_timeout()` 设置 `MAXDWORD/MAXDWORD/正数常量`；`ReadFile` 可立即返回已有字节。一次读取容量 256 字节，不要求填满 | PySerial 正超时的默认读法和 Rust 不同，不能直接搬用 `read(256)`；本机仍保留绝对期限和有界残片 |
| 10. 解析桥接包     | 本地队列按 16 字节取帧，检查头尾、帧标志和 ID；官方会跳过不合格字节/帧并继续找帧                                                         | 本机按约定保留损坏、未知和重复帧并故障，不照搬丢弃和重新同步行为                              |
| 11. 更新电机状态   | 按 arbitration ID 或电机 ID 匹配，解码状态、位置等，更新带锁的最新状态；寄存器反馈另存缓存和时间                                         | 正常状态缓存不提供每拍七轴完成证明，也没有协议命令事务号；本机继续验证完整七轴并只消费一次    |
| 12. 空闲与继续收包 | 已有可解析帧时持续处理；无帧或接收错误时线程 sleep 200 µs。零等待调用读入数据后还可能先返回 None，由后续调用解析                         | “后台一直收”不等于每个读取调用都返回帧。不能只看接收线程存在就认定有每拍完整反馈              |
| 13. 上层取观察     | `_read_feedback()` 逐轴请求反馈，手动 poll 一次，再 `get_state()` 取缓存；缓存非空即可返回                                               | 这与 Teacher 七轴新鲜度/序号/20 ms 整组完成要求不同；本轮保持原 Teacher 语义                  |
| 14. 关闭           | controller 停止接收线程，按关闭入口决定是否失能，再关闭总线                                                                              | 本机继续尝试全部七轴失能，迟到控制帧与独立新失能证据分开保留                                  |

旧固定版本的 `recv(0)` 在本地无完整帧时仍可能执行一次带 2 ms 串口超时的读取，并在读取后检查零时长期限；读取期间持有总线锁。新增参考的 `bytes_to_read()` 空队列检查减少了这条空闲读路径。两者均不能作为本机放宽 20 ms 的依据。

[Microsoft COMMTIMEOUTS](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-commtimeouts) 分别定义了 `MAXDWORD/0/0` 的立即返回模式和 `MAXDWORD/MAXDWORD/正数常量` 的首字节返回模式。本机此前的临时非阻塞读遵循前一种；官方 Rust Windows 实现使用后一种。两者需要按读取参数和整组期限比较，不能只比较 timeout 数值。

## 实际 Owner 分段测量

### 补核官方 Windows 写入

固定 `serialport 4.9.0` 的 `COMPort::open` 使用 `FILE_ATTRIBUTE_NORMAL` 创建同步句柄；`write()` 直接调用 `WriteFile(..., lpOverlapped=NULL)` 并返回实际字节数。PySerial 3.5 使用 `FILE_FLAG_OVERLAPPED`，随后调用 `GetOverlappedResult(..., true)` 等主机完成。两条路径都不提供电机执行 ACK，也都可能等待驱动；不能只删除后者的等待，或把尚未完成的异步写记作成功。[Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getoverlappedresult) 说明 `bWait=true` 在 I/O 未完成时等待；[Python ctypes 文档](https://docs.python.org/3.12/library/ctypes.html#ctypes.WinDLL) 说明 WinDLL 调用释放并重新取得 GIL，因此当前 wall time 不等于纯内核时间。

随后在已失能状态，只读查询与原两段数据完整验证并行，各使用独立进程；修正后的探针记录了原生完成调用进入时的状态与实际返回字节数。**600/600 组通过**，整组平均 / P99 / 最大 **8.341 / 9.386 / 10.379 ms**，开始和结束七轴失能、串口关闭；该次完成调用最大 0.327 ms，未复现 12 ms。4204 次写在进入完成调用时仍为 `STATUS_PENDING`，3 次已完成，证明不能把此步骤普遍当作无用调用删除。此对照没有正常 Owner 的力、主臂与校准检查，也没有同进程 trace/采集线程，不算控制路径通过。

状态探针早先版本错误地对 PySerial 直接传入的 OVERLAPPED 结构做指针转换，导致诊断进程异常退出，无有效输出；这些尝试不采用。已先用直接结构、byref、指针三种模拟输入检验原调用次数、字节数、身份和原异常，再运行上述修正版。没有把探针改动带入生产收发。

**当前结论仍是异步超时未解决。** 接收层已经减少重复管理调用，但发送完成及 Owner 恢复运行的长尾仍会耗尽原 20 ms。没有证据支持放宽期限、改用旧反馈、自动回退串行或删除写完成校验；本轮不更改这些语义。全阶段原记录、失败组及只读补测保留在 `phase_diagnostic/` 和 `native_completion_corrected_under_verification.json`。

## 原生边界与内核调度跟踪

本节证据位于 `outputs/async_native_boundary_20261029_1245/`。生产收发源码与上一轮正常候选的 SHA256 相同；以下 DLL、探针、WPR 配置仅在该诊断目录使用，没有装入正常采集入口。

### 当前异步与 20 ms 的含义

当前 pipelined 已将提交与反馈收集分开：同一串口 Owner 在轴间和两拍间服务接收，完整七轴快照由下一拍消费一次。它没有并行收发线程；当这个 Owner 的主机写完成调用阻塞时，它暂时不能服务接收。官方 MotorBridge 的接收线程与调用方发送可以并发调度，但二者仍共用串口锁；Windows 底层采用同步 `ReadFile/WriteFile`，并不保证所有调用立即返回。官方状态缓存也不等于本工程每拍新鲜完整七轴的要求。

20 ms 来自本工程原有 `send_budget_s=0.02`：`FullArmValidationSession.send()` 完成目标编码后，在 `pipeline.begin()`、准备总线及第一轴写入之前取 `started`，整组截止为 `started + send_budget_s`。七轴主机写入、发送间隔、接收和完整验证共用此绝对截止；下一拍或下一次读不重新计时。它不是每轴 20 ms、电机协议 ACK 期限或官方缓存承诺。50 Hz 的名义拍周期也为 20 ms，但计时起点不同；读预算 15 ms、拍保护 40 ms 等仍分别保留。

增加独立接收线程会改变当前唯一 Owner 的架构。本轮保持现有架构，不把“完全异步”解释为取消反馈完整性、写结果或停止验证。

### 区分原生调用与返回 Python 后的时间

诊断 C DLL 在真实 `GetOverlappedResult` 调用前后直接记录 QPC；调用次数、参数、返回值、完成字节数和线程错误值保持原样。外层另记 Python 进入/返回时间，避免把等待重新取得 GIL 的时间算进原生区间。ABI 自检覆盖 240 次真实普通文件 overlapped 写、直接结构/byref/指针输入、字节内容与未完成错误；不使用机械臂验证 ABI。
