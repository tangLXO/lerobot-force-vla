# 历史双阶段收发对照（2026-10-29）

用户所指的后续实现是：**一拍内主动查询七轴反馈 → 决策 → 提交七轴控制 → 收齐控制反馈**。它与更早的 100 Hz、每 10 ms 一组新目标是两条不同路径。不能把两者统称为重复发两遍控制命令。

本轮仅以这条历史路径提供诊断对照。按用户最后明确的要求，当前采集架构继续采用异步收发：**本拍提交七轴命令，由唯一 Owner 在发送间隙和两拍之间接收，下一拍消费完整反馈**。没有把历史同步双阶段改回控制路径。

## 核对旧源码和原始日志

桌面工作树 `134e6388` 的 `ForceRuntime.tick()` 在 `active_query` 路径先调用 `read_joint_snapshot()`，取得观察后再提交动作；`FullArmValidationSession.send()` 支持调用方的绝对截止时间；`continuous_control.py` 七次独立写入后集中收包。正常控制期限由 Runtime 从本拍开始计算并向下传递，发送阶段不能另起一个完整预算。

后续旧日志 `examples/force_teacher/diagnostics/20261027_followup/long_pause_rows.jsonl` 中，正常样例 tick 7336 明确记录了 7 次 `query_attempt`、7 次 `command_attempt`，且最后查询接收早于第一条控制写入，控制反馈随后收齐。该拍工作 11.1757 ms。该文件也包含故障上下文，正常样例不等于整场无超时。

更早的 `outputs/force_teacher_tuning/c5942db4bcee4c9495a537b52c0101c6/run/` 则有 8714 次正常七轴提交，约 99.579 Hz；60998 条命令包的 `sendTimes` 均为 1。那条路径复用上一拍新鲜、未消费的反馈，不能作为“同一条控制命令重复发送两次”的证据。

## 失能只读实验

沿用用户已授权的只读诊断。每拍预算 20 ms；两轮共用同一截止时间，第一轮失败时禁止发第二轮。所有发送均为映射或反馈查询，没有模式写入、使能或运动命令。

| 实验                                   | 完成拍数 | 两阶段平均 / P99 / 最大         | 结果                                          |
| -------------------------------------- | -------: | ------------------------------- | --------------------------------------------- |
| 两轮逐轴查询，首轮完整后立即开始第二轮 |     1500 | 7.314 / 9.831 / 11.840 ms       | 全部通过，零调度跳拍                          |
| 先完整查询，再以 120 µs 间隔连续查询   |     1500 | 7.712 / 9.652 / 17.824 ms       | 首段通过                                      |
| 上项重复                               |      110 | 正常拍 7.677 / 9.447 / 9.543 ms | 第 111 拍第二阶段未收齐末尾两轴，不能视为修复 |
| 先完整查询，再以 1000 µs 间隔连续查询  |     1500 | 12.058 / 14.731 / 16.035 ms     | 此段通过                                      |

第二阶段在这里仍是查询，不是真实控制；实验没有包含 I-P、实时力/主臂/校准检查及录制负载。因此只能证明通信容量及反例，不能用来授予真实控制或采集通过资格。所有会话串口关闭，通过的会话末尾均取得七轴失能反馈。

结果表明：20 ms 容纳两轮通信在当前设备上可行，但仅增加前置查询，仍不能消除过密连续发送的反馈缺失。这不支持把当前异步架构改成每拍同步双阶段，也不支持重发未知结果的控制命令。

## 当前实现边界

本轮曾加入 `active_observation_query` 实验开关及调用方期限传递；用户明确要求保留现有架构后，已撤回这部分以及对应测试。六个既有修改文件逐一比对修改前工作区快照，内容指纹一致；没有使用 HEAD 或远端代码覆盖工作区。新增的 Runtime 测试也单独撤回。

保留的新增内容仅为本报告和独立的 `two_rounds_readonly_hardware_smoke_test.py` 查询诊断及其测试；它们不被采集入口调用。撤回后相关回归 **142 passed**。既有异步实现、每拍完整七轴新反馈、原通信预算、停止路径及通用默认设置继续保持。
